### 22. Executable Native DNS Core Foundation
I have begun converting the first-party DNS architecture from source declarations into executable GoreeCloud-owned Go code. The initial native package is internal/gcdns. It is intentionally isolated from the inherited production request path while its contracts and behavior are validated.
The native core defines normalized DNS Request and Result types together with first-party Policy, Authority, Cache, Resolver, and Observer interfaces. These interfaces establish stable internal contracts for client/policy processing, authoritative-zone answers, cache access, recursive or forwarded resolution, and privacy-aware observability without requiring permanent AdGuard Home or Unbound runtime boundaries.
The initial Pipeline processes requests in this order: policy evaluation → authoritative DNS → cache lookup → recursive or forwarded resolution. This is a skeleton rather than a complete production resolver. It provides a deterministic coordination layer that can be unit-tested while individual native implementations are developed behind the interfaces.
The initial typed Config validates security-sensitive invariants before runtime integration. It requires at least one DNS listener, requires DNSSEC validation and DNS rebinding protection to remain enabled by default, requires explicit recursive-access networks when unrestricted public recursion is disabled, rejects unrestricted recursive networks in private-recursion mode, and rejects unrestricted administrative networks.
The repository now includes unit tests for the initial configuration safety invariants and a dedicated native-dns-core CI job that runs go test ./internal/gcdns. The architecture validator also requires the native core source files and verifies the first-party pipeline stage markers. These gates remain source and unit-test evidence only until an exact-head CI run is observed.
This package is not yet connected to production DNS traffic and does not retire or bypass the existing AdGuard Home or Unbound deployments. Future native work will implement concrete cache, authoritative, recursive resolver, policy/filtering, listener, DNSSEC, and observability components and will connect them to production-equivalent traffic only after isolated acceptance.

### 23. Native In-Memory DNS Cache Implementation
I will use the native GoreeCloud DNS cache as an internal first-party runtime subsystem rather than depending permanently on inherited AdGuard Home or Unbound cache behavior.
The initial implementation is internal/gcdns/cache.go. It uses power-of-two sharding and per-shard locks to reduce contention while a cache-wide read/write gate coordinates full-cache flush operations. Configured bounded capacity evicts the oldest entry within an affected shard. A zero MaxEntries value means unlimited capacity during development; bounded configurations must allocate at least one entry per shard.
Cache keys normalize the DNS question name, type, and class and currently include a client partition. ClientID is preferred and client IP is used as a fallback. This conservative partitioning prevents cross-client cache-state leakage while client policy, split-horizon behavior, and future cache-sharing scopes are still being implemented. A later explicit cache-scope model may safely broaden sharing after policy semantics are proven.
Cached DNS messages are copied on insertion and retrieval so downstream code cannot mutate shared cached state. Positive entries expire according to the CacheTTL supplied by the resolver result. Returned DNS resource-record TTLs are aged to the remaining cache lifetime. Expired entries are removed unless serve-stale is enabled and the entry remains inside the configured stale window. Stale responses are marked Stale=true, return CacheTTL=0, and expose zero wire TTL so callers do not treat stale data as freshly cacheable.
The initial cache recognizes NXDOMAIN and successful NODATA responses as negative entries for accounting and lifecycle purposes. Cache statistics expose hits, misses, stale hits, puts, evictions, total entries, and negative entries. These statistics are intended to feed GoreeCloud DNS observability without requiring raw query export.
The implementation includes deterministic clock injection so expiration and stale-window behavior can be tested without wall-clock sleeps. Tests cover copy isolation, DNS wire-TTL aging, normal expiration, bounded stale serving, negative-entry accounting, client partitioning, bounded eviction, invalid configuration, flush accounting, and concurrent access.
The source validator requires the cache implementation, TTL-aging behavior, flush serialization, negative-cache support, stale behavior, and the deterministic cache test set. CI is configured to run go test ./internal/gcdns, but source presence and validator contracts do not substitute for successful exact-head executable CI.
This implementation is not yet connected to the inherited production DNS request path. Persistent cache storage, aggressive negative caching, prefetch, auto-prefetch, cache persistence/recovery, cache warming, richer eviction policy, explicit cache-sharing scopes, and production integration remain staged work. Production use remains prohibited until correctness, DNSSEC interaction, load behavior, restart/recovery, memory bounds, privacy, observability, rollback, and target-environment acceptance are demonstrated.

### 23. Native Persistent Cache and Prefetch Foundation
I will implement persistent caching, prefetch, and auto-prefetch as first-party GoreeCloud DNS cache capabilities rather than as Unbound dependencies or external cache services.
The native persistent-cache implementation uses an explicitly supplied runtime path, a versioned on-disk format, packed DNS wire messages, owner-only temporary-file permissions, atomic replacement, and restore-time validation. Entries that are no longer usable under the active expiration or serve-stale policy are discarded during restore. Persistent cache files are runtime data and must follow GoreeCloud privacy, file-permission, data-protection, backup, recovery, and sensitive-information requirements; they are not source-controlled configuration.
The native prefetch layer tracks successful fresh-cache popularity and selects records for proactive refresh only after a configurable hit threshold and when the remaining positive TTL falls within a configurable refresh window. Candidate selection does not perform DNS network activity. A native resolver scheduler will later execute controlled refresh work so prefetch and auto-prefetch remain subject to cancellation, DNSSEC validation, normal resolver/forwarding policy, resource limits, observability, and administrative controls.
Source implementation status: draft PR #3 now contains internal/gcdns/cache_persistence.go, cache_persistence_test.go, cache_prefetch.go, and cache_prefetch_test.go in addition to the native in-memory cache. The fail-closed architecture validator requires these implementations, deterministic tests, persistence safety markers, and documented boundaries. This is source implementation progress, not production acceptance; persistence lifecycle automation, actual refresh scheduling, and native recursive resolution remain future implementation stages.

### 25. Beacon Resolver Scheduler and Proactive Refresh Execution
I will implement Beacon Resolver as the native scheduling and resolution-execution family inside GoreeCloud DNS. The initial scheduler foundation in internal/gcdns/resolver_scheduler.go provides bounded concurrent attempts across approved resolver targets, per-attempt timeouts, cancellation after the first valid response, failover, latency-aware ordering based on successful measured attempts, and privacy-safe target success/failure/latency statistics.
Canceled losing attempts are not recorded as resolver failures, and cancellation from the calling request is propagated rather than rewritten as an upstream failure. These rules are required so Beacon Insights can distinguish genuine target failure from expected concurrency cancellation and so resolver health data remains operationally meaningful.
The scheduler does not yet constitute a complete recursive resolver. TargetResolver implementations remain responsible for DNS transport, recursive delegation walking or forwarding/stub behavior, protocol validation, DNSSEC validation, response processing, and target-specific security controls. The scheduler provides the concurrency, timeout, selection, failover, cancellation, and health-accounting layer those implementations will use.
Beacon Cache proactive refresh now has an execution boundary in internal/gcdns/prefetch_runner.go. Prefetch candidates are executed through a complete RequestResolver such as the native Pipeline rather than by calling a network resolver directly. This preserves the normal policy, authoritative, cache, resolver, DNSSEC, cancellation, and observability path during prefetch and auto-prefetch work.
Deterministic source tests cover first-success selection, fallback after target failure, attempt timeout handling, scheduler configuration validation, bounded proactive-refresh concurrency, independent candidate failures, malformed candidates, and prefetch-runner configuration validation. This remains source-development evidence only until exact-head executable CI is observed.
Production impact remains none. Beacon Resolver scheduling and proactive-refresh execution are not connected to the inherited production request path, and the existing production DNS services remain unchanged pending complete native resolver implementation, protocol/DNSSEC correctness, load and failure testing, migration, rollback, and explicit acceptance

### 26. Beacon Resolver Classic DNS Transport Foundation
I will use a dedicated first-party classic DNS transport layer underneath the Beacon Resolver scheduler rather than embedding socket behavior directly into scheduling, cache, policy, or DNSSEC components.
The initial implementation is internal/gcdns/resolver_transport.go. Resolver targets now carry an explicit stable target ID, host:port address, and optional network selector. The classic transport defaults to UDP and supports TCP as an explicit target transport. It uses the existing miekg/dns dependency already present in the GoreeCloud DNS repository, so this milestone does not introduce a new DNS protocol library dependency.
The transport executes against caller context so ResolverScheduler attempt deadlines and cancellation remain authoritative. It defensively copies DNS requests before exchange and validates that returned messages are marked as responses, preserve the expected transaction ID, preserve question count, and match the original question name, type, and class. Invalid or mismatched responses fail closed rather than being promoted into the resolver pipeline.
UDP truncation is handled explicitly. When TCP fallback is enabled, a truncated UDP response is retried over TCP against the same target. A truncated TCP response is rejected. When fallback is disabled, a truncated UDP response is also rejected rather than being treated as a successful final answer. This prevents the scheduler from accepting incomplete DNS messages as valid resolver outcomes.
The transport uses a narrow DNSExchanger interface so deterministic unit tests can exercise protocol-control behavior without opening live network sockets. The test set covers normal UDP execution, UDP-to-TCP truncation fallback, fail-closed truncation when fallback is unavailable, response transaction-ID mismatch, question mismatch, invalid target addressing, unsupported transport selection, and caller cancellation.
This transport layer does not yet provide recursive delegation walking, root-hints/bootstrap management, referral and glue processing, DNSSEC chain validation, trust-anchor lifecycle, QNAME minimization, forward-zone policy, encrypted DNS transport, or cache-TTL normalization. Those remain separate Beacon Resolver and Beacon Secure DNS implementation stages so transport mechanics cannot silently substitute for resolver correctness or DNSSEC trust.
Production impact remains none. The native transport is isolated inside internal/gcdns and is not connected to the inherited production DNS request path. Existing AdGuard Home and Unbound services remain unchanged pending isolated runtime validation, protocol and DNSSEC correctness, load/failure testing, migration, rollback proof, and explicit production acceptance.

### 27. Beacon Resolver Iterative Recursion Foundation
I will use Beacon Resolver to perform recursive DNS resolution locally inside GoreeCloud DNS rather than forwarding recursive responsibility permanently to an external resolver product. The current source-development milestone adds the first bounded iterative delegation walker in internal/gcdns/iterative_resolver.go and keeps it isolated from production DNS traffic.
The iterative resolver starts from approved root/bootstrap targets, clears the recursion-desired bit on authoritative queries, uses the shared ResolverScheduler for each authoritative target set, follows NS referrals, and terminates on answers, DNS error responses, or authoritative negative responses. ResolverScheduler now exposes ResolveTargets so delegation-specific target sets reuse the same concurrency, timeout, cancellation, latency ordering, and privacy-safe target-health accounting rather than creating a separate recursion scheduler. Scheduler response classification also treats SERVFAIL, REFUSED, NOTIMP, and FORMERR as retryable target failures so a fast unhealthy authority cannot win ahead of another valid target; NXDOMAIN remains a legitimate terminal DNS result.
Referral processing is deliberately fail-closed. The current implementation accepts A and AAAA glue only when the address belongs to a name server explicitly advertised by the referral and that name server is in-bailiwick for the delegated zone. Out-of-bailiwick Additional-section addresses are ignored rather than trusted. A referral with no usable in-bailiwick glue currently fails because recursive address discovery for out-of-bailiwick authoritative name servers remains a later implementation stage.
The walker enforces a configurable maximum delegation depth and records delegation state so repeated delegation target sets are rejected as loops. Terminal positive responses receive cache lifetimes derived from the minimum answer TTL. Authoritative NXDOMAIN and NODATA responses use an SOA-bounded negative-cache lifetime based on the lower of the SOA record TTL and SOA MINIMUM value.
The repository now includes internal/gcdns/root_hints.go with independent IPv4 and IPv6 targets for the 13 root authorities listed by IANA. I reviewed the official IANA root-server registry on August 21, 2026 before recording the bootstrap set, including the current B-root addresses 170.247.170.2 and 2801:1b8:10::b. These compiled bootstrap targets are a source foundation rather than a permanent update mechanism; a controlled runtime root-hints refresh and validation lifecycle remains required.
Deterministic tests cover a successful referral walk, recursion-desired suppression, IPv4 and IPv6 in-bailiwick glue extraction, rejection of out-of-bailiwick glue, delegation-loop detection, negative-cache TTL derivation, and the current B-root bootstrap values. The fail-closed resolver validator now requires the scheduler, classic DNS transport, root bootstrap, iterative walker, and their test markers as part of the native first-party DNS source contract.
This milestone does not complete recursive DNS. DNSSEC chain validation and root trust anchors, DS and DNSKEY processing, out-of-bailiwick name-server address discovery, CNAME and DNAME chasing, QNAME minimization, lame-delegation handling, EDNS policy, richer retry behavior, authoritative integration, and target-environment runtime acceptance remain required before production use.
Production impact remains none. I did not change the running AdGuard Home or Unbound services, DNS clients, NetBird nameserver, DHCP service, authoritative zones, encrypted DNS endpoints, Caddy configuration, firewall state, credentials, or production cutover state.

### 28. Beacon Resolver DNSSEC Validation Foundation
I will treat DNSSEC validation as a first-party Beacon Resolver trust function rather than relying permanently on an external recursive resolver to establish DNS authenticity. The current source-development milestone introduces internal/gcdns/dnssec_validator.go and explicit DNSSEC validation states in the native Result contract.
The result model now distinguishes indeterminate, insecure, secure, and bogus DNSSEC outcomes. Indeterminate means the available primitive cannot establish a trust conclusion. Insecure represents an authenticated or explicitly modeled unsigned delegation boundary. Secure represents successful cryptographic validation against trusted DNSKEY material. Bogus represents validation failure and must fail closed rather than being treated as ordinary unsigned DNS.
The initial validator verifies uniform DNS RRsets against matching trusted DNSKEY and RRSIG material, checks RRSIG inception and expiration windows, and uses the existing miekg/dns cryptographic verification implementation. It also provides DS-to-DNSKEY matching for supported SHA-1, SHA-256, and SHA-384 DS digests. A delegation with no DS is represented as insecure; a supported DS/DNSKEY mismatch is bogus; and a delegation whose DS set contains no supported digest remains indeterminate rather than being silently accepted.
The native Pipeline now refuses resolver results marked DNSSECBogus before they can be inserted into Beacon Cache. DNSSEC status is also propagated into the privacy-aware Observer event contract so Beacon Insights can eventually report validation outcomes without requiring raw query export.
Deterministic source tests cover DS/DNSKEY matching and mismatch, unsigned delegation state, missing signature/key material as indeterminate, non-uniform RRset rejection, and fail-closed pipeline behavior for bogus results. The fail-closed source validator now requires the DNSSEC validator, its test markers, the four DNSSEC result states, and the pipeline bogus-result boundary.
This milestone is not a complete DNSSEC chain validator. Root trust-anchor storage, RFC 5011-style rollover lifecycle, iterative acquisition and authentication of DS and DNSKEY RRsets, DNSKEY RRset self-validation, NSEC and NSEC3 authenticated denial, wildcard proof validation, algorithm policy, trust-chain state across referrals, and validation of every terminal response remain required before DNSSEC production acceptance.
Production impact remains none. The DNSSEC primitives are isolated inside internal/gcdns and are not connected to the inherited production DNS request path. Existing AdGuard Home and Unbound services, DNS clients, NetBird nameserver configuration, DHCP, authoritative zones, encrypted DNS endpoints, firewall state, credentials, and production cutover state remain unchanged.

### 29. Beacon Resolver Root Trust Anchors and Signed Delegation Validation
I will maintain DNSSEC trust-chain validation as a first-party Beacon Resolver responsibility. The current source-development milestone adds a built-in IANA root trust-anchor set, root DNSKEY authentication primitives, signed child-delegation validation primitives, and DNSSEC-request signaling for iterative queries.
The built-in root trust-anchor set currently contains the IANA-published SHA-256 DS records for KSK-2017 with key tag 20326 and KSK-2024 with key tag 38696. I verified the current IANA rollover state on August 21, 2026. IANA identifies KSK-2017 as active, KSK-2024 as pre-publication, and schedules the rollover for October 11, 2026. Both anchors are therefore carried during the transition window. This source set is a bootstrap and development foundation rather than a permanent substitute for an authenticated runtime trust-anchor update and rollover lifecycle.
The new root DNSKEY validator requires the DNSKEY RRset to contain at least one key whose computed DS matches a configured root trust anchor. It then validates the DNSKEY RRset signature using only anchor-matched keys. A missing DNSKEY RRset, missing DNSKEY signature, anchor mismatch, or signature failure is treated as bogus rather than accepted as unsigned DNS.
The signed-delegation validator requires authenticated parent DNSKEY material, a signed child DS RRset from the parent, a child DNSKEY RRset whose key material matches the authenticated DS set, and a valid DNSKEY RRset signature. The validator deliberately does not infer that a delegation is insecure merely because DS records are missing. Missing DS proof remains indeterminate until NSEC or NSEC3 authenticated denial is implemented and validated.
Beacon Resolver iterative queries now set the EDNS DNSSEC OK bit and request at least a 1232-byte UDP payload while preserving larger preexisting EDNS UDP sizes. This allows authoritative servers to return DS, DNSKEY, and RRSIG material needed by the future end-to-end chain without enabling recursive behavior on upstream authorities.
Deterministic tests cover the current root-anchor identities and digests, the KSK-2017 public-key-to-anchor match, rejection of missing root DNSKEY material, DNSSEC EDNS signaling, signed-delegation material extraction, refusal to classify missing DS as insecure without authenticated denial, and child-zone DNSKEY material boundaries.
This work still does not wire complete DNSSEC trust validation through every iterative resolution. The remaining production-critical stages include root DNSKEY acquisition during resolver startup or resolution, secure parent-key state across referrals, child DNSKEY queries at every signed delegation, NSEC/NSEC3 authenticated denial, wildcard proof handling, algorithm policy, trust-anchor persistence and automated rollover state, complete terminal RRset validation, and runtime acceptance. Production impact remains none; the existing AdGuard Home and Unbound services, NetBird DNS assignment, DHCP, Caddy, firewall, and client configuration remain unchanged.

### 30. Beacon Resolver Iterative DNSSEC Trust-Chain Execution
I now have a dedicated first-party DNSSEC-validating iterative resolver path in GoreeCloud DNS. I use DNSSECIterativeResolver to connect the previously implemented root trust anchors, DNSSEC cryptographic validator, signed-delegation validator, resolver scheduler, and iterative authority walk into one controlled trust-chain execution path.
The validating resolver first queries the approved root authorities for the root DNSKEY RRset and authenticates that RRset against the configured root trust-anchor set. After root authentication succeeds, I carry the authenticated parent DNSKEY state through the iterative delegation walk instead of treating each referral as an independent untrusted transition.
At every signed child delegation, the resolver obtains the child zone DNSKEY RRset from the newly selected authoritative targets. It then validates the parent-signed DS RRset, matches the child DNSKEY material to the authenticated DS records, validates the child DNSKEY RRset signature, and adopts the child keys only after the transition reaches the secure validation state. A failed or indeterminate transition does not silently continue as secure recursion.
For terminal positive answers, I group returned data by owner name and RR type, require an RRSIG for every positive RRset, restrict candidate authenticated DNSKEYs to the RRSIG signer zone, and validate the RRset before I return DNSSECSecure. If no authenticated signer key exists for a terminal RRset, the response fails closed rather than being accepted or cached.
I continue to treat negative DNSSEC answers conservatively. NXDOMAIN and NODATA are not accepted as authenticated merely because the response is authoritative or because a DS record is absent. The validating iterative path currently fails closed until I implement NSEC and NSEC3 authenticated-denial verification. Wildcard proof validation remains part of the same required trust work.
I added deterministic source tests covering root-key acquisition, authenticated parent-key carry across a referral, child DNSKEY acquisition, secure terminal positive-answer handling, signer-zone key filtering, rejection when no authenticated terminal signer key exists, negative-answer fail-closed behavior, and required trust inputs. I also added scripts/validate_dnssec_iterative.py and expanded scripts/validate_resolver_backend.py so the integrated resolver source contract requires the root-anchor, signed-delegation, iterative-DNSSEC, signer-key, documentation, and test layers. The lint workflow runs the focused DNSSEC source-contract validator, while the native-dns-core job remains responsible for go test ./internal/gcdns.
This milestone remains source development rather than production acceptance. GitHub has not provided successful exact-head workflow evidence for this work, and I have not connected DNSSECIterativeResolver to the inherited production DNS request path. ### 31. Beacon Resolver Authenticated Denial of Existence
I will treat authenticated denial of existence as part of the first-party Beacon Resolver DNSSEC trust chain rather than accepting unsigned negative responses or inferring nonexistence from DNS response codes alone. I require the denial material itself to be cryptographically authenticated before its semantics are trusted. ### 32. Beacon Resolver Authenticated Insecure Delegation State
I will not treat a missing DS record in a referral as sufficient evidence that a delegated child is unsigned. Beacon Resolver must authenticate DS absence with the secure parent before crossing from a secure DNSSEC chain into an insecure subtree.
The current native implementation adds DNSSECValidator.ValidateInsecureDelegation. It accepts conservative proof forms only: an exact-name signed NSEC at the delegated child with NS present and DS absent, or an exact-name signed NSEC3 that matches the delegated child with NS present and DS absent. Every NSEC, NSEC3, and other denial RRset used by the proof must validate against authenticated parent-zone DNSKEY material. NSEC3 opt-out remains unsupported and fails closed.
After authenticated DS absence is established, the resolver changes its trust state to DNSSECInsecure, does not fetch or require a child DNSKEY RRset, and returns terminal data within that unsigned subtree as insecure rather than secure or bogus solely because it lacks DNSSEC signatures. The insecure state persists through deeper referrals. A deeper DS record cannot restore secure status because an unsigned parent cannot authenticate that DS record. A separate explicit trust anchor would be required to re-establish a secure chain and is outside this milestone.
This behavior prevents accidental trust resurrection beneath an authenticated insecure boundary. Proofs that advertise DS, do not identify an actual delegation, lack required signatures, use inconsistent NSEC3 parameters, or depend on unsupported NSEC3 opt-out semantics are rejected or remain indeterminate.

Implementation Update — Integrity-Bound Beacon Filter-List Ingestion
I extended the Beacon policy-control foundation with `internal/gcdns/policy_filterlist.go`. `BuildPolicyFilterListRules` accepts a reviewed filtering-list snapshot only when the exact content matches a mandatory caller-supplied SHA-256 digest, then compiles supported DNS-domain entries into the existing `PolicyRule` model. The implementation therefore reuses existing profile assignment, deterministic precedence, schedules, privacy-minimized policy decisions, aggregate policy statistics, and production isolation rather than creating a parallel filtering engine.
The source parser is deliberately bounded to an 8 MiB snapshot, 500,000 lines, and 4096 bytes per line. It currently accepts bare DNS domain names, `||domain^` DNS-domain anchors, `@@` allow exceptions, and hosts-file entries using conventional sinkhole addresses `0.0.0.0`, `127.0.0.1`, `::`, and `::1`. Unsupported browser-only filter syntax, arbitrary hosts-file destination addresses, malformed integrity metadata, and ambiguous normalized allow/block entries fail closed instead of being guessed.
Equivalent normalized entries collapse deterministically. Generated filtering-rule IDs use stable counters rather than embedding filtered domain names. Same-list `@@` exceptions compile one priority level above that list's block rules so exception behavior is explicit rather than depending on rule-ID sort order; a maximum integer base priority with an allow exception is rejected because there is no safe precedence level remaining.
This milestone is an integrity-bound local ingestion primitive, not a complete managed-list service. It does not yet download mutable remote URLs, silently refresh subscriptions, or claim authenticated source provenance. Required follow-up includes authenticated provenance and signed metadata, controlled acquisition, update scheduling, freshness and expiry rules, rollback history, source-trust policy, multi-list conflict policy, privacy-governed operational state, and Everkeep-backed recovery/portability for managed list configuration.
